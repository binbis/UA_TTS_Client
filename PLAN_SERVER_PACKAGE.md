# План: окремий виконуваний сервер (Linux + Windows), без Python у користувача

> Тимчасовий план. Реалізовано етапи 1–4, 6–7 (2026-11-22). Етап 5 частково: Windows-колеса підтверджено, запуск exe на Windows ще не перевірено (потрібна Windows-машина/ВМ). Етап 8 — документація (частково вже в процесі).
> Після завершення всіх етапів план перенести в `Doc/Roadmap.md`, файл видалити.
> Режим: користувач отримує готовий zip. Збірка виконується один раз (локально на Linux або GitHub Actions для обох ОС), не користувачем.
>
> Статус рішень:
> - Формат: **PyInstaller `onedir`** — тека, не один файл. Виконавчий файл лежить **поруч з publish клієнта**.
> - Запуск сервера: **тільки вручну**, без консолі з клієнта; консоль доступна при запуску подвійним кліком.
> - Клієнт: кнопка запуску/зупинки + перегляд логу. Автозапуску і запуску по `Alt+Q` нема.
> - Модель (~911 МБ): качається **при першому запуску** у теку даних користувача, далі працює офлайн.
> - Збірка: GitHub Actions (Windows + Linux), локальна збірка на Arch — як запасний варіант.

## Етап 1. ✅ Портативність `Server_py/server.py`

Мета: сервер працює однаково з `run_server.sh`, з термінала і як заморожений exe.

Задачі:
1. Ввести `BASE_DIR`: якщо `sys.frozen` — тека поруч з exe, інакше — тека `server.py`.
2. Від `BASE_DIR` шукати `voices/*.pt` і `dictionary.json` (зараз — від CWD, небезпечно).
3. Зробити `HF_HOME` (кеш моделі) за замовчуванням у теку даних користувача:
   - Linux: `~/.local/share/ua-tts/hf` (або `~/.cache/ua-tts/hf`);
   - Windows: `%LocalAppData%\UA_TTS\hf`;
   - якщо `HF_HOME` уже задано — поважати його.
4. Додати логування:
   - кожен вивід — одночасно в консоль і у файл `logs/server.log` рядом з даними користувача;
   - ротація за розміром, щоб файл не ріс безмежно;
   - першим рядком друкувати: версія, пристрій (`cuda/cpu`), кількість голосів, шлях до логу;
   - на Windows примусово UTF-8 для консолі.
5. Мінімальний `argparse`: `--log-file`, `--log-level`. Без `console=False` (див. Етап 2).
6. Додати режим самоперевірки `--check` (для CI): перевіряє імпорти критичних модулів (`torch`, `flask`, `styletts2_inference`, `ukrainian_word_stress`, `ipa_uk`, `verbalizer`) і виходить **до** завантаження моделі — без завантаження 911 МБ.
7. `multiprocessing.freeze_support()` для Windows-збірки.

Файли: `Server_py/server.py`, за необхідності `Server_py/verbalizer.py` (не змінювати логіку).

Критерії прийняття:
- `run_server.sh` працює так само, як раніше (регресія відсутня).
- Сервер, запущений з іншої теки, знаходить голоси і словник.
- Існує запис у лозі після старту; `/api/health` повертає ті самі поля.
- CORS-заголовки не змінюються (їх використовує розширення браузера).

## Етап 2. ✅ PyInstaller-пакет сервера

Мета: готовий тека-артефакт `UA_TTS_Server/` з exe всередині.

Задачі:
1. Створити `Server_py/packaging/UA_TTS_Server.spec`:
   - режим `onedir` (не `onefile`);
   - `console=True` — консоль видно при ручному запуску; клієнт запускатиме без вікна;
   - hidden imports за потреби: `flask`, `pydub`, `pypdf`, `docx`, `odf`, `ukrainian_word_stress`, `ipa_uk`, `deep_translator`, `scipy`;
   - `collect_all` для `transformers` + `torch` + `scipy`/`librosa` (data-файли і бінарники всередині);
2. `voices/*.pt` і файл `dictionary.json` пакуються **зовні**, поруч з exe — користувач може додавати голоси і правити словник без перезбірки.
3. `ffmpeg` всередину пакета: покласти бінарник на етапі збірки (через `imageio-ffmpeg` або готовий бінарник), прибрати runtime-завантаження `static_ffmpeg` при старті, щоб сервер працював офлайн.
4. Python для збірки — **3.12** (не 3.14: під нього гарантовано є torch-колеса).
5. Порядок встановлення залежностей при збірці:
   1. `pip install torch --index-url https://download.pytorch.org/whl/cu128` (CUDA);
   2. `pip install -r requirements.txt pyinstaller`.

Файли: `Server_py/packaging/UA_TTS_Server.spec`, `Server_py/packaging/README` (коротко: як зібрати вручну, якщо CI недоступний).

Критерії прийняття:
- `dist/UA_TTS_Server/UA_TTS_Server` (Linux) і `UA_TTS_Server.exe` (Windows) стартують без системного Python у PATH.
- `/api/health` відповідає після завантаження моделі.
- Один синтез на CPU працює (перевірка модуля `ukrainian-tn` на Windows — див. Етап 5).
- Пакет працює зі зміненим CWD.

Ризики: torch + Rust-колесо `ukrainian-tn` на Windows ще не запускались; можливі hidden imports, які виявляються тільки практикою.

## Етап 3. ✅ GitHub Actions — збірка обох артефактів

Мета: обидва exe збираються в хмарі, користувач отримує готові zip, Windows-машина не потрібна.

Задачі:
1. Створити `.github/workflows/build-server.yml`:
   - тригер: `workflow_dispatch` (вручну) + теги `server-v*`;
   - два джоби, бо перехресної компіляції нема:
     - Linux: `ubuntu-latest` (або Arch-образ) → Linux-exe;
     - Windows: `windows-latest` → Windows-exe;
   - Python 3.12, кеш pip;
   - кроки: встановити torch CUDA → встановити `requirements.txt` + `pyinstaller` → `pyinstaller packaging/UA_TTS_Server.spec` → smoke-тест → zip → artifact;
2. Smoke-тест у CI: запустити `UA_TTS_Server --check` (імпорти працюють), перевірити, що exe існує, і **не** завантажувати модель (911 МБ у CI — дорого; повну перевірку робити локально, Етап 4);
3. Артефакти:
   - `UA_TTS_Server-linux-x86_64.zip`;
   - `UA_TTS_Server-windows-x64.zip`;
   - прикріплення до GitHub Release при тегу.
4. Локальна збірка на Arch лишається як запасний варіант — ті самі команди, що й у CI (док — `Server_py/packaging/README`).

Критерії прийняття:
- Ручний запуск workflow створює два zip-артефакти.
- Жоден джоб не вимагає GPU (на GitHub-ранерах GPU нема — це нормально: CUDA-бібліотеки приїжджають у torch-колесах і працюватимуть на GPU користувача).

## Етап 4. ✅ Перевірка на Linux (ваша Arch-машина)

Задачі:
1. Зібрати Linux-пакет локально (команди з Етапу 3) та/або завантажити артефакт CI.
2. Перевірити на «чистому» середовищі: прибрати `/usr/bin/python` з PATH, запустити exe, дочекатись `/api/health`, зробити один синтез.
3. Перевірити перший запуск з порожнім кешем (`HF_HOME`): модель завантажилась, повторний запуск працює офлайн.

Критерії прийняття: сервер працює без системного Python; логи пишуться; голоси і словник читаються з теки пакета.

## Етап 5. ⚠️ Перевірка на Windows

Задачі:
1. Завантажити Windows-артефакт CI на чисту Windows 11 (ВМ або реальна машина).
2. Перевірити: подвійний клік → консоль з логами → `/api/health` → синтез; окремо — з CUDA-GPU і без неї (CPU-фолбек).
3. Особливо перевірити: `ukrainian-tn` (Rust-колесо), `static-ffmpeg`, шляхи з пробілами і кирилицею, створення теку даних у `%LocalAppData%`.

Критерії прийняття: Windows-exe працює без встановленого Python; синтез на CUDA якщо є GPU; інакше — на CPU без помилок.

Якщо Windows не заведеться — зафіксувати причину в `Doc/reference/Pitfalls.md` і вирішити (CPU-збірка як запасний артефакт, або фікс імпортів).

## Етап 6. ✅ Керування сервером з клієнта

Мета: ручні кнопки «Запустити / Зупинити» і перегляд логу, без консолі і без автозапуску.

Задачі:
1. Новий сервіс `IServerProcessService` (`Infrastructure/Process/`, реєструється тільки в `App.axaml.cs`):
   - шукає exe: типово `<appdir>/Server/UA_TTS_Server(.exe)`;
   - у налаштуваннях — поле «Шлях до сервера» (якщо пакет розпаковано в інше місце);
   - `Start`: `UseShellExecute=false`, `CreateNoWindow=true`, без примусового CWD; stdout/stderr — у `logs/server.log`; після старту полінг `/api/health` кожні 2 с до готовності, статус «Запуск моделі… (перший раз — хвилини)», скасування через `CancellationToken`;
   - `Stop`: `Process.Kill(entireProcessTree: true)`;
   - якщо `/api/health` відповідає, а наш процес не запущений — статус «Порт 5000 зайнятий іншою програмою», чужий процес не вбивати;
   - при виході клієнта сервер **лишається працювати**; наступного разу клієнт його «підхоплює» через health;
2. UI (за правилами репо: `partial` ViewModel, `x:DataType`, українською): кнопки запуску/зупинки, статус, кнопки «Показати лог» (останні рядки) і «Відкрити файл логу»;
3. Автозапуску і запуску по `Alt+Q` не робити (рішення користувача).

Після цього етапу: `dotnet build` — 0 warnings, 0 errors; ручна перевірка за `Doc/development/Manual_Test_Scenarios.md` (додати сюди сценарії запуску/зупинки сервера).

## Етап 7. ✅ Фінальна роздача користувачу

Структура роздачі (клієнт і сервер — окремі артефакти, кладуться поруч):

```
UA_TTS/
├── UA_TTS_Client(.exe)         # dotnet publish self-contained, linux-x64 / win-x64
├── bass.dll                    # тільки Windows
└── Server/
    ├── UA_TTS_Server(.exe)
    ├── _internal/
    ├── voices/*.pt
    └── dictionary.json
```

Задачі:
1. `dotnet publish` self-contained для обох ОС (окремо від сервера).
2. Два zip: `UA_TTS_Client_linux.zip` + `UA_TTS_Server_linux.zip`, аналогічно Windows.
3. Перевірити, що тека `Server/` — у записуваному місці (не Program Files): пакету потрібні кеш моделі, логи і `voices/`.

## Свідомо поза планом (не робити в v1)

- Автозапуск сервера / запуск по `Alt+Q`.
- Акуратний `POST /api/shutdown` (CORS `*` робить це небезпечним без токена).
- `console=False` + `--console` (консоль при ручному запуску і так є; перегляд логу з клієнта її замінює).
- Пакет з моделлю всередині (модель — 911 МБ, качається при першому старті).
- CPU-варіант пакета (тільки якщо розмір CUDA-пакета 2.5–4 ГБ виявиться неприйнятним).
- Nuitka / `onefile` (див. Етап 2 — `onedir` обрано свідомо).
